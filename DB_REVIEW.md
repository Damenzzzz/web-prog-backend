# Zhibek Lite: переход на PostgreSQL — полный разбор

Документ для защиты Assignment 6: что было, что сделали, зачем, и как это всё связано.

---

## 1. Что было и что стало

**Было (Assignment 5).** Все данные лежали в словарях Python в `app/storage.py`:

```python
items: dict[int, dict] = {}
users: dict[int, dict] = {}
orders: dict[int, dict] = {}
...
_last_ids = {"item": 0, "user": 0, ...}
```

Проблемы:
- после перезапуска сервера всё пропадало (словари живут в оперативной памяти процесса);
- id выдавал самодельный счётчик `next_id()`;
- связи между данными держались только на честном слове кода: никто не мешал записать в заказ несуществующий `item_id`;
- два процесса uvicorn не видели бы данные друг друга.

**Стало (Assignment 6).**
- данные лежат в **PostgreSQL** — отдельном сервере базы данных, на диске;
- Python общается с базой через **SQLAlchemy** (ORM);
- структура таблиц описывается **миграциями Alembic**;
- связи и правила проверяет не только код, но и сама база (внешние ключи, `CHECK`, `UNIQUE`);
- всё поднимается одной командой через **Docker Compose**.

Что не поменялось: эндпоинты, Pydantic-схемы, бизнес-правила, фронт. Клиент (сайт и Swagger) разницы не видит, кроме того,
что данные больше не теряются.

## 2. Какие технологии и за что каждая отвечает

| Что | Версия | Роль |
|---|---|---|
| **PostgreSQL** | 16 (образ `postgres:16-alpine`) | сервер базы данных: хранит таблицы на диске, следит за ограничениями, даёт транзакции |
| **SQLAlchemy** | 2.x | ORM: позволяет работать с таблицами как с классами Python (`User`, `Item`), сам пишет SQL |
| **psycopg** | 3.x (`psycopg[binary]`) | драйвер: низкоуровневая библиотека, через которую SQLAlchemy реально подключается к PostgreSQL по сети |
| **Alembic** | 1.x | миграции: создаёт и меняет структуру таблиц по версиям |
| **Pydantic** | 2.x | валидация входящих запросов и формирование ответов (как и раньше) |
| **Docker Compose** | — | поднимает два контейнера (база + приложение) и связывает их сетью |
| **pytest** | — | автотесты API на отдельной тестовой базе |

Цепочка вызова при запросе:

```
Браузер / Swagger
   │  HTTP
   ▼
FastAPI router  (app/routers/*.py)      — принял запрос, Pydantic проверил тело
   │  db: Session = Depends(get_db)
   ▼
Service         (app/services/*.py)     — бизнес-правила, работа с моделями
   │  db.get(...), db.scalars(select(...)), db.commit()
   ▼
SQLAlchemy ORM  (app/models.py)         — превращает объекты в SQL
   │  psycopg
   ▼
PostgreSQL      (контейнер zhibek-lite-db)
```

### Почему PostgreSQL, а не SQLite
- так требует задание;
- настоящий сервер: несколько подключений одновременно, блокировки строк (`FOR UPDATE`), настоящие enum-типы;
- так делают в продакшене.

### Что такое ORM и зачем он
ORM (Object-Relational Mapping) — прослойка, которая связывает класс Python с таблицей.
Вместо `INSERT INTO users (name, ...) VALUES (...)` пишем:

```python
user = User(name="Айгерим", height_cm=165, ...)
db.add(user)
db.commit()
```

SQLAlchemy сам сформирует SQL, отправит его и положит в `user.id` номер, который выдала база.

## 3. Подключение: `app/db.py`

```python
DATABASE_URL = os.getenv("DATABASE_URL", "postgresql+psycopg://zhibek:zhibek@localhost:5433/zhibek")
engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine, autoflush=False, expire_on_commit=False)

class Base(DeclarativeBase):
    pass

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

Разбор строки подключения `postgresql+psycopg://zhibek:zhibek@localhost:5433/zhibek`:

| Кусок | Значение |
|---|---|
| `postgresql` | тип базы |
| `+psycopg` | драйвер (psycopg 3) |
| `zhibek:zhibek` | логин:пароль |
| `localhost:5433` | хост и порт (5433 снаружи Docker; внутри compose — `db:5432`) |
| `/zhibek` | имя базы |

Берётся из переменной окружения `DATABASE_URL` (требование задания: «configure through environment variables»).
В Docker её подставляет `docker-compose.yml`, локально — `.env` или значение по умолчанию.

| Объект | Что это |
|---|---|
| `engine` | «двигатель»: знает, куда подключаться, держит пул соединений. Один на всё приложение |
| `SessionLocal` | фабрика сессий |
| `Session` | «рабочая сессия» с базой: копит изменения, отправляет их при `commit()`, откатывает при `rollback()` |
| `Base` | базовый класс всех моделей; в `Base.metadata` хранится описание всех таблиц (его читает Alembic) |
| `get_db()` | FastAPI-зависимость: открывает сессию на **один запрос** и гарантированно закрывает её в `finally` |

Параметры сессии:
- `autoflush=False` — SQLAlchemy не отправляет изменения в базу «сам по себе» перед каждым запросом, только когда мы явно делаем `commit`;
- `expire_on_commit=False` — после `commit()` объекты не «протухают», их можно сразу вернуть в ответ без лишнего запроса.

### Как сессия попадает в код

```python
@router.get("/users/{user_id}", response_model=UserOut)
def get_user(user_id: int, db: Session = Depends(get_db)):
    return users_service.get_user(db, user_id)
```

Роутер получает `db` через `Depends`, передаёт в сервис первым аргументом. **`commit` делает сервис**, потому что только
он знает, где заканчивается одна бизнес-операция. Если в сервисе вылетела ошибка до `commit`, сессия закрывается, и
PostgreSQL откатывает незавершённые изменения — в базе не остаётся «половины» операции.

Роутеры стали обычными `def` вместо `async def`: сессия SQLAlchemy синхронная, и FastAPI сам запускает такие функции в
отдельном потоке, чтобы не блокировать сервер. `async` остались только там, где есть `await`: загрузка фото
(`await file.read`) и примерка (`await llm.generate_try_on`).

## 4. Таблицы и колонки: `app/models.py`

Всего **8 таблиц** + служебная `alembic_version`.

### Схема связей

```
                 ┌─────────┐
                 │  looks  │
                 └────┬────┘
                      │ 1
                      │
                      │ N
┌───────────────┐   ┌─┴──────┐   ┌──────────────┐
│ try_on_items  │>──│ items  │──<│ order_items  │
└───────┬───────┘   └───┬────┘   └──────┬───────┘
        │               │ 1             │ N
        │ N             │               │
        │               │ N             │ 1
┌───────┴───────┐   ┌───┴───────────────┐   ┌──────────┐
│   try_ons     │   │ fitting_room_rows │   │  orders  │
└───────┬───────┘   └───┬───────────────┘   └────┬─────┘
        │ N             │ N                      │ N
        │               │                        │
        └──────────┐    │    ┌───────────────────┘
                   │ 1  │ 1  │ 1
                 ┌─┴────┴────┴─┐
                 │    users    │
                 └─────────────┘
```

`1 ─< N` — один-ко-многим. `try_on_items` — таблица-связка для многие-ко-многим.

### 4.1 `looks` — готовые образы

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PRIMARY KEY, автоинкремент | номер образа |
| `title` | `VARCHAR(100)` | NOT NULL, **UNIQUE** | название; двух одинаковых образов быть не может |

Связь: один образ → много товаров (`Look.items`). У модели есть свойство `item_ids` — список id товаров образа, его
отдаёт `GET /looks`.

### 4.2 `items` — товары каталога

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер товара |
| `name` | `VARCHAR(100)` | NOT NULL | название |
| `category` | enum `category` | NOT NULL | `top`, `bottom`, `outerwear`, `shoes`, `bag`, `accessory` |
| `color` | `VARCHAR(30)` | NOT NULL | цвет (для подбора «дополни образ») |
| `price` | `INTEGER` | NOT NULL, **CHECK price > 0** | цена в тенге, целым числом |
| `stock` | `INTEGER` | NOT NULL, **CHECK stock >= 0** | остаток на складе |
| `look_id` | `INTEGER` | FK → `looks.id`, **ON DELETE SET NULL**, индекс | к какому образу относится; может быть пустым |
| `image_url` | `VARCHAR(255)` | может быть NULL | путь к фото в `static/` |

Почему `price` целым числом, а не `float`: деньги во `float` теряют копейки при округлении.

`ON DELETE SET NULL` — если образ удалят, товар не пропадёт, просто станет «без образа».

### 4.3 `users` — профиль

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер пользователя |
| `name` | `VARCHAR(50)` | NOT NULL | имя |
| `height_cm` | `INTEGER` | NOT NULL, **CHECK 100..250** | рост |
| `weight_kg` | `INTEGER` | NOT NULL, **CHECK 30..250** | вес |
| `gender` | enum `gender` | NOT NULL | `female`, `male` |
| `body_type` | enum `body_type` | NOT NULL | `slim`, `average`, `athletic`, `plus` |
| `style_preference` | `VARCHAR(200)` | может быть NULL | любимый стиль |
| `photo_url` | `VARCHAR(255)` | может быть NULL | путь к загруженному фото |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, по умолчанию `now()` | когда создан (ставит сама база) |

Связи (все один-ко-многим): `fitting_room`, `orders`, `try_ons`.

Ограничения роста и веса продублированы: Pydantic отвечает 422 ещё до базы, а `CHECK` в базе страхует, если кто-то
запишет данные в обход API (например, через psql).

### 4.4 `fitting_room_rows` — примерочная (корзина)

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер строки |
| `user_id` | `INTEGER` | FK → `users.id`, **ON DELETE CASCADE**, индекс | чья корзина |
| `item_id` | `INTEGER` | FK → `items.id`, **ON DELETE RESTRICT** | какой товар |
| `quantity` | `INTEGER` | NOT NULL, **CHECK quantity >= 1** | сколько штук |

Плюс **`UNIQUE(user_id, item_id)`** — один товар в корзине одного пользователя только одной строкой. Повторное
добавление увеличивает `quantity`, а не создаёт дубль (это и сервис проверяет, и база гарантирует).

Раньше корзина была `storage.fitting_rooms[user_id] = [...]` — список внутри словаря. Теперь это отдельная таблица,
и «корзина пользователя» — просто все строки с его `user_id`.

- `CASCADE` по пользователю: удалили пользователя → его корзина удаляется автоматически;
- `RESTRICT` по товару: нельзя удалить товар, пока он лежит в чьей-то корзине.

### 4.5 `orders` — заказы

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер заказа |
| `user_id` | `INTEGER` | FK → `users.id`, **ON DELETE CASCADE**, индекс | кто заказал |
| `total` | `INTEGER` | NOT NULL, **CHECK total >= 0** | сумма |
| `status` | enum `order_status` | NOT NULL | `pending`, `paid`, `shipped`, `cancelled` |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, `now()` | когда оформлен |

Связь: один заказ → много позиций (`Order.items`).

### 4.6 `order_items` — позиции заказа

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер позиции |
| `order_id` | `INTEGER` | FK → `orders.id`, **ON DELETE CASCADE**, индекс | к какому заказу |
| `item_id` | `INTEGER` | FK → `items.id`, **ON DELETE SET NULL**, может быть NULL | какой товар был |
| `name` | `VARCHAR(100)` | NOT NULL | **снапшот** названия на момент заказа |
| `price` | `INTEGER` | NOT NULL, **CHECK price > 0** | **снапшот** цены на момент заказа |
| `quantity` | `INTEGER` | NOT NULL, **CHECK quantity >= 1** | сколько штук |

Зачем хранить `name` и `price`, если есть `item_id`? Потому что товар потом могут переименовать, поменять цену или
удалить. Заказ — это исторический документ: в нём должна остаться цена, по которой реально купили. Поэтому при удалении
товара `item_id` становится `NULL`, а название и цена в заказе остаются.

### 4.7 `try_ons` — AI-примерки

| Колонка | Тип | Ограничения | Зачем |
|---|---|---|---|
| `id` | `INTEGER` | PK | номер примерки |
| `user_id` | `INTEGER` | FK → `users.id`, **ON DELETE CASCADE**, индекс | чья примерка |
| `status` | enum `try_on_status` | NOT NULL | `done` или `failed` |
| `source` | `VARCHAR(10)` | NOT NULL | `gemini` или `mock` |
| `result_url` | `VARCHAR(255)` | может быть NULL | путь к картинке-результату |
| `error` | `VARCHAR(500)` | может быть NULL | текст ошибки, если Gemini отказал |
| `created_at` | `TIMESTAMPTZ` | NOT NULL, `now()` | когда сделана — по этой колонке считается лимит 3 в сутки |
| `deleted_at` | `TIMESTAMPTZ` | может быть NULL | **мягкое удаление** (добавлено второй миграцией) |

### 4.8 `try_on_items` — связка примерка ↔ товары (многие-ко-многим)

| Колонка | Тип | Ограничения |
|---|---|---|
| `try_on_id` | `INTEGER` | FK → `try_ons.id`, ON DELETE CASCADE, часть PK |
| `item_id` | `INTEGER` | FK → `items.id`, ON DELETE CASCADE, часть PK |

Первичный ключ составной: `(try_on_id, item_id)`. Одна примерка — несколько вещей, одна вещь — во многих примерках.
Раньше это был список `item_ids: [1, 2]` внутри словаря; в реляционной базе списки так не хранят, для этого и нужна
таблица-связка. В модели это `relationship(secondary=try_on_items)`, а свойство `item_ids` собирает список для ответа API.

### 4.9 `alembic_version` — служебная

Одна колонка `version_num`, одна строка: номер последней применённой миграции (сейчас `33e0dbb57cf0`). По ней Alembic
понимает, какие миграции уже накатаны, а какие нет.

### 4.10 Enum-типы в PostgreSQL

В базе созданы 5 собственных типов: `category`, `gender`, `body_type`, `order_status`, `try_on_status`. Это
настоящие типы PostgreSQL: в колонку `category` физически нельзя записать `"hat"` — база ответит ошибкой.
Значения берутся из тех же `StrEnum`, что и в Pydantic-схемах (`app/schemas/*.py`), поэтому API и база не разойдутся.

## 5. Связи: виды и примеры

| Вид | Где | Как в коде |
|---|---|---|
| **один-ко-многим** | `looks` → `items` | `Item.look_id = ForeignKey("looks.id")`, `Look.items = relationship(back_populates="look")` |
| **один-ко-многим** | `users` → `orders` | `Order.user_id`, `User.orders` |
| **один-ко-многим** | `users` → `fitting_room_rows` | `FittingRoomRow.user_id`, `User.fitting_room` |
| **один-ко-многим** | `users` → `try_ons` | `TryOn.user_id`, `User.try_ons` |
| **один-ко-многим** | `orders` → `order_items` | `OrderItem.order_id`, `Order.items` |
| **многие-к-одному** | `fitting_room_rows` → `items` | `FittingRoomRow.item = relationship()` |
| **многие-ко-многим** | `try_ons` ↔ `items` | таблица `try_on_items`, `TryOn.items = relationship(secondary=...)` |

Разница между `ForeignKey` и `relationship`:
- `ForeignKey` — это **колонка и ограничение в базе**: «в этом поле может быть только существующий id из другой таблицы»;
- `relationship` — это **удобство в Python**: позволяет писать `user.orders` или `row.item.price` вместо ручного
  запроса. В базе от него ничего не появляется.

`back_populates` связывает две стороны: `Order.user` и `User.orders` — это одна и та же связь, увиденная с двух концов.

### Что происходит при удалении (`ondelete`)

| Правило | Где | Смысл |
|---|---|---|
| `CASCADE` | всё, что принадлежит пользователю; позиции заказа; связка примерок | удалили «родителя» → дети удаляются автоматически |
| `RESTRICT` | `fitting_room_rows.item_id` | нельзя удалить товар, пока на него ссылается корзина |
| `SET NULL` | `items.look_id`, `order_items.item_id` | родителя удалили → ссылка обнуляется, сама запись остаётся |

В моделях ещё стоит `cascade="all, delete-orphan", passive_deletes=True`. Это значит: удаление делает **сама база** по
`ON DELETE CASCADE`, а SQLAlchemy не грузит всех детей в память, чтобы удалить их по одному.

## 6. Миграции и Alembic

### Что такое миграция

Миграция — это **файл с кодом, который меняет структуру базы** (создаёт таблицу, добавляет колонку, индекс и т. д.) и
умеет это изменение **откатить**. Миграции нумеруются и применяются по порядку.

Аналогия: Git для структуры базы. Код приложения хранится в Git с историей коммитов; структура таблиц — в миграциях с
историей версий.

### Зачем они нужны

1. **Воспроизводимость.** Любой человек клонирует репозиторий, делает `alembic upgrade head` и получает точно такую же
   схему. Требование задания: «schema can be recreated by applying the migrations».
2. **Изменения без потери данных.** Когда нужна новая колонка, мы не удаляем базу и не создаём её заново — миграция
   делает `ALTER TABLE ... ADD COLUMN`, старые данные остаются. Именно так добавили `deleted_at`.
3. **История.** Видно, когда и какое изменение схемы появилось.
4. **Откат.** Если миграция оказалась неудачной, `alembic downgrade -1` возвращает предыдущую версию.
5. **Одинаковая схема везде**: у тебя, у напарника, в Docker, в тестах.

Альтернатива — `Base.metadata.create_all()`. Она умеет только создать таблицы с нуля и **не умеет менять** уже
существующие. Поэтому её мы не используем.

### Что такое Alembic

Alembic — инструмент миграций от авторов SQLAlchemy. Он:
- сравнивает модели в `app/models.py` с реальной базой и **сам генерирует** миграцию (`--autogenerate`);
- хранит номер текущей версии в таблице `alembic_version`;
- применяет и откатывает миграции командами.

### Файлы Alembic в проекте

| Файл | Зачем |
|---|---|
| `alembic.ini` | конфиг: где лежат миграции (`script_location = alembic`), настройки логов |
| `alembic/env.py` | точка входа: берёт `engine` из `app/db.py` (значит, тот же `DATABASE_URL`) и `Base.metadata` из `app/models.py` — так Alembic знает, с какой базой работать и какие таблицы должны быть |
| `alembic/script.py.mako` | шаблон, по которому генерируются новые файлы миграций |
| `alembic/versions/*.py` | сами миграции |

### Наши миграции

**1. `9d8d32b3736c_initial_schema.py`** — `down_revision = None` (первая).

- `upgrade()`: `create_table` для всех 8 таблиц со всеми колонками, PK, FK, `CHECK`, `UNIQUE`, индексами и enum-типами.
  Порядок важен: сначала `looks` и `users`, потом `items` (ссылается на `looks`), потом всё, что ссылается на них.
- `downgrade()`: удаляет таблицы в обратном порядке **и вручную удаляет enum-типы**. Это дописано руками: autogenerate
  удаляет таблицы, но не типы, и тогда повторный `upgrade` падает с «type category already exists».

**2. `33e0dbb57cf0_soft_delete_for_try_ons.py`** — `down_revision = '9d8d32b3736c'`.

- `upgrade()`: `op.add_column('try_ons', sa.Column('deleted_at', sa.DateTime(timezone=True), nullable=True))`
- `downgrade()`: `op.drop_column('try_ons', 'deleted_at')`

Зачем она: лимит «3 примерки в сутки» считается по строкам `try_ons`. Если бы удаление примерки удаляло строку,
пользователь мог бы удалить и сразу сделать новую — бесконечно тратя Gemini. Поэтому удаление мягкое: ставим
`deleted_at`, удаляем картинку, а строка остаётся для подсчёта. В API удалённая примерка не видна (404 и нет в списке).

Связь между миграциями — через `revision` / `down_revision`: каждая знает своего «родителя», получается цепочка
`None → 9d8d32b3736c → 33e0dbb57cf0 (head)`.

### Команды

```bash
alembic upgrade head                        # применить все ещё не применённые миграции
alembic downgrade -1                        # откатить одну последнюю
alembic downgrade base                      # откатить все (база пустая)
alembic current                             # какая версия сейчас в базе
alembic history                             # список миграций
alembic revision --autogenerate -m "..."    # сгенерировать новую по изменениям в models.py
```

Как добавить новую колонку (сценарий для защиты):
1. Дописать поле в класс в `app/models.py`.
2. `alembic revision --autogenerate -m "add xxx"` — Alembic сравнит модели с базой и создаст файл.
3. Проверить файл глазами (autogenerate не всё угадывает, например переименования).
4. `alembic upgrade head`.
5. Закоммитить файл миграции вместе с изменением модели.

В Docker миграции применяются автоматически при каждом старте контейнера:
`CMD ["sh", "-c", "alembic upgrade head && uvicorn ..."]`. Если всё уже применено, Alembic ничего не делает.

## 7. Docker: какую базу подняли и как

Файл `docker-compose.yml`, проект `zhibek-lite`, два сервиса.

**`db` → контейнер `zhibek-lite-db`**
- образ `postgres:16-alpine`;
- `POSTGRES_USER/PASSWORD/DB = zhibek` — при первом запуске создаётся пользователь и база;
- порт `5433:5432` — снаружи 5433 (чтобы не конфликтовать с другими Postgres на машине), внутри стандартный 5432;
- volume `pgdata:/var/lib/postgresql/data` — **файлы базы лежат в именованном томе Docker**, поэтому переживают
  перезапуск и пересоздание контейнера;
- `healthcheck` с `pg_isready` — Docker знает, когда база реально готова принимать подключения.

**`app` → контейнер `zhibek-lite`**
- собирается из `Dockerfile`;
- `env_file: .env` — ключ Gemini и настройки;
- `DATABASE_URL: postgresql+psycopg://zhibek:zhibek@db:5432/zhibek` — внутри сети compose база доступна по имени
  сервиса `db`, а не `localhost`;
- порт `8090:8000`;
- volumes `uploads` и `results` — фото пользователей и результаты примерок тоже не пропадают;
- `depends_on: db: condition: service_healthy` — приложение стартует только после того, как база готова.

Проверить базу руками:

```bash

\dt                       -- список таблиц
\d items                  -- колонки и ограничения таблицы
```

## 9. Сервисы: CRUD и бизнес-правила по файлам

Основные приёмы SQLAlchemy, которые встречаются в коде:

| Код | Что делает | SQL примерно |
|---|---|---|
| `db.get(User, 5)` | найти по первичному ключу | `SELECT ... WHERE id = 5` |
| `db.scalars(select(Item).where(...))` | список объектов по условию | `SELECT ... WHERE ...` |
| `db.scalar(select(...))` | один объект или `None` | `SELECT ... LIMIT 1` |
| `db.add(obj)` | пометить новый объект на вставку | `INSERT` при commit |
| `obj.field = value` | изменить | `UPDATE` при commit |
| `db.delete(obj)` | пометить на удаление | `DELETE` при commit |
| `db.commit()` | отправить всё одной транзакцией | `COMMIT` |
| `db.rollback()` | отменить | `ROLLBACK` |
| `db.refresh(obj)` | перечитать объект из базы | `SELECT` |

### `services/items.py` — каталог
- **Create** `create_item`: если указан `look_id`, проверяем, что образ есть (иначе 404), потом `Item(**data)`.
- **Read** `list_items`: фильтры стали частью SQL-запроса (`.where(Item.category == ...)`, `func.lower(Item.color)`),
  база фильтрует сама, а не Python по всему списку.
- **Update** `update_item`: теперь `exclude_unset` вместо `exclude_none` — это позволяет явно отправить
  `"look_id": null` и убрать товар из образа. А `null` для обязательных полей (`name`, `price` …) → 400.
- **Delete** `delete_item`: если товар в чьей-то корзине → 409 (и база то же самое запретила бы через `RESTRICT`).
- `find_matches` («дополни образ»): кандидатов по категории и наличию отбирает SQL, сочетание цветов проверяет Python.

### `services/users.py` — профиль
- Обычный CRUD.
- `delete_user`: если есть заказ `pending` или `paid` → 409. Иначе `db.delete(user)` — база каскадом удаляет корзину,
  заказы и примерки, после `commit` удаляются файлы фото и результатов.
- Файлы удаляем **после** commit: если бы удаление из базы не прошло, файлы остались бы на месте.

### `services/fitting_room.py` — примерочная
- `add_item`: проверки «пользователь есть», «товар есть», «не больше 10 позиций», «не больше остатка». Если строка уже
  есть — увеличиваем `quantity`, иначе создаём `FittingRoomRow`.
- `update_quantity`, `remove_item`: работают со строкой таблицы, если её нет → 404.

### `services/orders.py` — заказы (самое интересное)
`create_order` — одна транзакция:
1. берём строки корзины пользователя; пусто → 400;
2. загружаем товары с **`with_for_update()`** → `SELECT ... FOR UPDATE`: строки товаров блокируются до конца
   транзакции. Если два пользователя одновременно покупают последнюю вещь, второй подождёт первого и увидит уже
   уменьшенный остаток;
3. остатка не хватает → `rollback`, 409;
4. уменьшаем `stock`, создаём `Order` и `OrderItem` со снапшотом названия и цены, удаляем строки корзины;
5. `commit` — всё применяется разом. Либо заказ оформлен целиком, либо ничего не изменилось.

`change_status`: допустимые переходы `pending → paid → shipped`, `pending/paid → cancelled`; остальное → 409.
При отмене остатки возвращаются на склад (если товар ещё существует).

### `services/try_on.py` — AI-примерка
- лимит 3 в сутки — теперь SQL-запрос `COUNT(*)` по `try_ons` за последние 24 часа (раньше — отдельный словарь `try_on_times`);
- запись создаётся и коммитится **до** вызова Gemini со статусом `failed`. Если Gemini упадёт, ошибка сохраняется в
  `error`, делается `commit`, клиент получает 502 — попытка остаётся в истории и в лимите;
- нельзя дважды передать один и тот же товар (иначе нарушился бы составной PK в `try_on_items`) → 400;
- удаление мягкое (`deleted_at`).

## 10. Валидация и целостность — три уровня защиты

| Уровень | Чем | Пример | Ответ |
|---|---|---|---|
| 1. Входные данные | Pydantic-схемы | `height_cm: 50`, `category: "hat"`, `quantity: 0` | 422 `validation_error` |
| 2. Бизнес-правила | сервисы | нет такого пользователя; больше остатка; пустая корзина; нельзя `pending → shipped` | 404 / 400 / 409 |
| 3. Целостность | ограничения PostgreSQL | FK на несуществующий id, `stock < 0`, дубль в корзине | `IntegrityError` → 409 `conflict` |

Третий уровень — страховка: при нормальной работе до него не доходит, потому что сервисы проверяют раньше. Но если в
коде будет ошибка или кто-то полезет в базу напрямую, PostgreSQL не даст записать мусор.

Все ошибки приходят в одном формате: `{"error": "...", "detail": "..."}`.

## 14. Вопросы, которые могут задать, и короткие ответы

**Зачем Alembic, если можно `create_all()`?** `create_all` только создаёт отсутствующие таблицы и не умеет менять
существующие. Миграции меняют схему, не теряя данные, и хранят историю.

**Что будет, если удалить пользователя?** Если есть заказ `pending`/`paid` — 409. Иначе база по `ON DELETE CASCADE`
удалит его корзину, заказы с позициями и примерки, сервис удалит файлы.

**Почему в `order_items` дублируются `name` и `price`?** Это снапшот: заказ должен помнить цену на момент покупки, даже
если товар потом изменят или удалят.

**Чем `ForeignKey` отличается от `relationship`?** FK — ограничение в базе. `relationship` — удобный доступ в Python
(`user.orders`), в базе его нет.

**Почему одна сессия на запрос?** Сессия не потокобезопасна и копит изменения. Своя сессия на каждый запрос изолирует
запросы друг от друга, а `finally: db.close()` гарантирует, что соединение вернётся в пул даже при ошибке.

**Что такое транзакция и где она?** Группа изменений, которая применяется целиком или никак. Каждый `commit` в сервисе
закрывает транзакцию; самый показательный пример — `create_order`.

**Зачем `FOR UPDATE`?** Чтобы два параллельных заказа не продали одну и ту же последнюю вещь.

**Зачем индексы на `user_id`, `look_id`, `order_id`?** Поиск «все заказы пользователя», «все товары образа» идёт по
этим колонкам; индекс делает его быстрым, а не перебором всей таблицы.

**Почему порт 5433?** Внутри контейнера стандартный 5432, снаружи 5433, чтобы не конфликтовать с другими Postgres на машине.

**Где хранятся данные физически?** В Docker volume `pgdata`. `docker compose down` его не трогает, `docker compose down -v` удаляет.

**Почему мягкое удаление примерок?** Чтобы удаление не сбрасывало дневной лимит 3 примерки.

## 15. Честно о слабых местах

- **Нет авторизации.** Пользователь — это просто `user_id` в localStorage браузера; любой может обратиться к чужому id.
  В задании не требовалось.
- **Примерка синхронной сессией внутри `async`.** `create_try_on` — `async` из-за запроса в Gemini, а сессия
  синхронная, так что запросы к базе там на мгновение блокируют event loop. Для учебного проекта некритично; правильно —
  `AsyncSession` или вынести запрос к Gemini отдельно.
- **Запросы с ленивой загрузкой.** `GET /looks` грузит товары каждого образа отдельным запросом (проблема N+1).
  На 4 образах незаметно; решается `selectinload`.
- **Пароль базы `zhibek` в `docker-compose.yml`.** Для локальной разработки нормально, для продакшена — в секреты.
- **`downgrade` удаляет данные.** Откат первой миграции удаляет все таблицы — это ожидаемо, но на живой базе так делать нельзя.
- **Файлы и база не в одной транзакции.** Если сервер упадёт между записью файла и `commit`, может остаться лишний файл
  в `static/uploads`. Данные в базе при этом не испортятся.
