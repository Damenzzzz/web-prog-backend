# Аутентификация и авторизация — разбор для защиты

## 1. Два слова, которые путают

- **Аутентификация** — «кто ты?». Проверяем email и пароль, выдаём токен, потом по токену узнаём пользователя.
- **Авторизация** — «что тебе можно?». Пользователь уже известен, решаем, пускать ли его к этому действию.

Ошибки соответствуют этим словам:

| Код | Значит | Пример |
|---|---|---|
| 401 | не знаем, кто ты | нет токена, токен подделан или просрочен, неверный пароль |
| 403 | знаем, кто ты, но нельзя | пользователь 2 смотрит заказы пользователя 1; не-админ создаёт товар |

## 2. Путь запроса

```
POST /auth/register ─► Pydantic проверяет данные ─► email занят? 409 ─► bcrypt-хеш ─► INSERT users
POST /auth/login    ─► ищем по email ─► bcrypt.checkpw ─► не совпало? 401 ─► выдаём JWT
GET /users/1/orders  + заголовок Authorization: Bearer <JWT>
        │
        ▼
get_current_user  (app/dependencies.py)
   нет заголовка → 401
   подпись не сходится / срок вышел → 401
   пользователя с таким id уже нет → 401
        │ User
        ▼
ensure_owner_or_admin(1, user)  →  не владелец и не админ → 403
        │
        ▼
обычный сервис, как и раньше
```

## 4. Почему так

**Почему хеш, а не пароль?** Если базу украдут, пароли не узнают. Хеш односторонний: из него пароль не получить,
можно только захешировать введённый пароль ещё раз и сравнить. Так делает `bcrypt.checkpw`.

**Почему bcrypt, а не sha256?** sha256 быстрый: видеокарта перебирает миллиарды паролей в секунду. bcrypt специально
медленный. Ещё у bcrypt своя случайная **соль** у каждого хеша, поэтому одинаковые пароли дают разные хеши
и готовые таблицы хешей (rainbow tables) бесполезны. Соль хранится прямо внутри строки хеша (`$2b$12$<соль><хеш>`).

**Почему пароль до 72 символов?** bcrypt учитывает только первые 72 байта. Чтобы не было сюрпризов, длиннее не принимаем (422).

**Что внутри JWT?** Три части через точку: `header.payload.signature`. В payload лежат `sub` (id пользователя) и
`exp` (когда истекает). Payload **не зашифрован**, его может прочитать кто угодно (base64), поэтому пароль туда не кладём.
Зато он **подписан** `SECRET_KEY`: если поменять `sub` на чужой id, подпись не сойдётся → 401. Это проверяет тест
`test_protected_endpoint_with_bad_tokens` (поддельный ключ, просроченный токен, мусор).

**Где хранится токен на сервере?** Нигде. JWT stateless: серверу достаточно проверить подпись, в базу за сессией
ходить не нужно. Поэтому **logout** — это когда фронт удаляет токен из `localStorage`. Минус: украденный токен живёт до
`exp`, поэтому срок короткий (60 минут). Refresh-токены и чёрный список мы сознательно не делали, чтобы не усложнять.

**Почему при входе одинаковая ошибка для «нет email» и «неверный пароль»?** Иначе по ответам можно узнать,
какие email зарегистрированы.

**Почему через регистрацию нельзя стать админом?** `register` не берёт `role` из запроса: даже если прислать
`"role": "admin"`, Pydantic отбросит лишнее поле, а роль будет `user` (тест `test_register_cannot_make_admin`).
Админ создаётся при старте из `.env`.

**Почему `HTTPBearer(auto_error=False)`?** Без этого FastAPI сам отвечает на отсутствие заголовка в своём формате.
Мы забираем это на себя и отвечаем 401 в общем формате `{"error", "detail"}`, как и остальные ошибки проекта.

**Почему 403, а не 404 на чужой ресурс?** 403 честно говорит «нельзя», и это проще объяснить и проверить.
404 скрыл бы сам факт существования ресурса. Это чуть безопаснее, но на учебном проекте не нужно.

**Почему URL остались `/users/{id}/...`, а не `/me/...`?** Так меньше переделок в фронте и тестах, и админ может
открыть данные любого пользователя тем же URL. Проверка `ensure_owner_or_admin` — одна строка.

**Почему токен проверяется через `Depends`?** Это переиспользуемая зависимость: написали один раз и подключаем
к любому эндпоинту. FastAPI сам вызывает её перед функцией и подставляет результат. Плюс в Swagger появляется кнопка Authorize.

**Почему миграция удаляет старых пользователей?** Новые колонки `email` и `password_hash` обязательные (NOT NULL),
а у старых анкет их нет, и войти в них всё равно нельзя. Их примерочная, заказы и примерки удаляются через `ON DELETE CASCADE`.

## 5. Таблица прав

| Действие | Гость | User | Admin |
|---|---|---|---|
| Смотреть товары, образы, «дополни образ» | ✅ | ✅ | ✅ |
| Создать / изменить / удалить товар | 401 | 403 | ✅ |
| Список всех пользователей | 401 | 403 | ✅ |
| Своя анкета, фото, примерочная, заказы, примерки | 401 | ✅ | ✅ |
| Чужие | 401 | 403 | ✅ |
| Заказ → `paid` или `cancelled` | 401 | ✅ свой | ✅ |
| Заказ → `shipped` | 401 | 403 | ✅ |

`shipped` ставит только админ: покупатель платит и может отменить заказ, а отправляет магазин.

## 6. Возможные вопросы

- *Чем отличается 401 от 403?* — см. раздел 1.
- *Можно ли расшифровать JWT?* — Прочитать можно (это base64), подделать нельзя без `SECRET_KEY`.
- *Что будет, если украдут `SECRET_KEY`?* — Можно будет выпустить токен на любого пользователя. Поэтому ключ лежит в `.env`,
  а не в коде, и `.env` в `.gitignore`.
- *Что будет с токеном, если пользователя удалили?* — `get_current_user` не найдёт его в базе → 401 (тест `test_token_of_deleted_user`).
- *Почему email в нижнем регистре?* — Чтобы `Aigerim@Mail.kz` и `aigerim@mail.kz` не стали двумя аккаунтами.
- *Как проверить в Swagger?* — `/auth/login` → скопировать `access_token` → Authorize → вставить.
