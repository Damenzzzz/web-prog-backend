# Zhibek Lite — полный разбор кода

Документ для подготовки к защите. Порядок: общая картина → базовые понятия (FastAPI, Pydantic, async, ООП) → каждый файл по функциям → LLM → фронт → слабые места → вопросы, которые могут задать.

---

## 1. Что это за проект

Бэкенд и лёгкий фронт магазина одежды с AI-примеркой. Пользователь:

1. смотрит каталог и готовые образы;
2. заполняет анкету (рост, вес, тип фигуры) и загружает своё фото;
3. складывает вещи в примерочную (это корзина);
4. оформляет заказ и меняет его статус;
5. запускает AI-примерку: Gemini «надевает» выбранные вещи на его фото.

Базы данных нет. Все данные лежат в словарях Python в оперативной памяти и пропадают при перезапуске сервера.

### Стек и зачем каждая библиотека

| Библиотека | Зачем |
|---|---|
| `fastapi` | Веб-фреймворк: связывает URL с функциями Python, проверяет входные данные, строит документацию |
| `pydantic` | Описание и проверка данных через классы. FastAPI работает на нём |
| `uvicorn` | Сервер, который принимает HTTP-запросы и передаёт их в FastAPI. Сам FastAPI запросы из сети не слушает |
| `httpx` | HTTP-клиент с поддержкой `async`. Через него идёт запрос к Gemini |
| `python-multipart` | Разбор форм с файлами. Без него FastAPI не примет `UploadFile` |

Нужен Python 3.11 или новее: в коде есть `StrEnum` (появился в 3.11) и запись типов `int | None` (с 3.10). В Docker используется 3.12.

## 2. Архитектура: три слоя

```
HTTP-запрос
    │
    ▼
routers/    принять запрос, вызвать сервис, вернуть ответ      (знает про HTTP)
    │
    ▼
services/   бизнес-правила, проверки, расчёты                   (не знает про HTTP)
    │
    ▼
storage.py  словари с данными                                   (не знает ни про что)
```

Сбоку стоят:

- `schemas/` — Pydantic-модели. Проверяют данные на входе в роутер и на выходе из него.
- `exceptions.py` — классы ошибок. Сервис бросает ошибку, обработчик превращает её в HTTP-ответ.
- `llm.py` — единственное место, которое ходит во внешний сервис (Gemini).

### Зачем так делить

- **Роутеры получаются в одну строку.** Вся логика в сервисах, её можно читать и проверять без HTTP.
- **Сервисы переиспользуют друг друга.** Например, `fitting_room.add_item` вызывает `users_service.get_user` и `items_service.get_item` и получает готовую проверку «существует ли» с ошибкой 404.
- **Хранилище можно заменить.** Чтобы перейти на базу данных, меняются сервисы и `storage.py`, роутеры и схемы остаются как есть.

### Путь одного запроса

Запрос `POST /users/1/fitting-room/items` с телом `{"item_id": 3, "quantity": 2}`:

1. Uvicorn принимает запрос и передаёт его приложению FastAPI.
2. FastAPI перебирает маршруты и находит `add_item` в [app/routers/fitting_room.py:14](app/routers/fitting_room.py#L14).
3. FastAPI готовит аргументы функции: `user_id` берёт из пути и превращает в `int`, тело запроса превращает в объект `FittingRoomAdd`. Если `quantity` равно 0 или `item_id` не число, клиент сразу получает 422, функция даже не вызывается.
4. Роутер вызывает `fitting_room_service.add_item(user_id, data)`.
5. Сервис проверяет: есть ли пользователь (иначе 404), есть ли товар (иначе 404), не превышен ли лимит в 10 позиций (иначе 400), хватает ли товара на складе (иначе 400).
6. Сервис меняет словарь `storage.fitting_rooms` и возвращает словарь с содержимым примерочной.
7. FastAPI прогоняет результат через `response_model=FittingRoomOut`, превращает в JSON и отдаёт с кодом 201.

Если на шаге 5 брошено исключение, шаги 6–7 не выполняются: обработчик из `exceptions.py` отдаёт JSON вида `{"error": "not_found", "detail": "Item 3 not found"}`.

## 3. Базовые понятия

### 3.1. FastAPI

**Декоратор маршрута.** `@router.get("/items/{item_id}")` говорит: «когда придёт GET на этот адрес, вызови функцию ниже». Имя метода декоратора — это HTTP-метод.

| Метод | Смысл в проекте |
|---|---|
| GET | Прочитать, ничего не меняя |
| POST | Создать новое (товар, анкету, заказ, примерку) |
| PATCH | Изменить часть полей существующего |
| DELETE | Удалить |

**Откуда FastAPI берёт аргументы функции.** Он смотрит на имя и тип каждого параметра:

| Как объявлен параметр | Откуда берётся | Пример |
|---|---|---|
| Имя совпадает с `{...}` в пути | Из URL | `item_id: int` |
| Тип — Pydantic-модель | Из JSON в теле запроса | `data: ItemCreate` |
| Тип — `UploadFile` | Из формы с файлом | `file: UploadFile` |
| Всё остальное | Из строки запроса после `?` | `color: str \| None = None` |

Типы здесь не просто подсказки: FastAPI по ним преобразует и проверяет значения. `/items/abc` при `item_id: int` даёт 422.

**`Query(...)`** добавляет ограничения к параметру строки запроса. `Query(4, ge=1, le=20)` значит: по умолчанию 4, допустимо от 1 до 20.

**`response_model`** — модель ответа. Делает три вещи:

1. проверяет, что функция вернула данные правильной формы;
2. **отбрасывает лишние поля**, которых нет в модели;
3. попадает в документацию.

**`status_code`** — код успешного ответа. По умолчанию 200, для создания ставим 201, для удаления 204 (ответ без тела).

**`APIRouter`** — группа маршрутов. Параметр `prefix` дописывается к каждому пути в группе, `tags` группирует эндпоинты в документации. Роутеры подключаются к приложению через `app.include_router`.

**Документация.** По адресу `/docs` FastAPI сам строит Swagger: список всех эндпоинтов с формами для отправки запросов. Строится из декораторов, типов параметров и Pydantic-моделей, вручную ничего писать не нужно.

### 3.2. Pydantic

Pydantic позволяет описать форму данных как класс. При создании объекта он проверяет типы и ограничения, а при ошибке сообщает, какое поле неверно.

```python
class ItemCreate(BaseModel):
    name: str = Field(min_length=1, max_length=100)
    price: int = Field(gt=0)
    look_id: int | None = None
```

- `BaseModel` — базовый класс всех моделей.
- `Field(...)` — ограничения: `min_length`, `max_length` для строк и списков, `gt` (строго больше), `ge` (больше или равно), `le` (меньше или равно) для чисел.
- Первый аргумент `Field` — значение по умолчанию. `Field(1, ge=1)` значит «по умолчанию 1, минимум 1». Если значения по умолчанию нет, поле обязательное.
- `int | None = None` — поле необязательное.

**Обязательное, необязательное и «может быть null» — разные вещи.** В `TryOnOut` поле `result_url: str | None` объявлено без значения по умолчанию. Значит, поле должно присутствовать всегда, но его значением может быть `null`.

**`model_dump()`** превращает объект модели в обычный словарь. В проекте так данные попадают в хранилище. `model_dump(exclude_none=True)` пропускает поля со значением `None`: это нужно для PATCH, чтобы менять только то, что прислал клиент.

**`StrEnum`** — перечисление, значения которого являются строками. `Category.top == "top"` даёт `True`. Pydantic принимает только значения из списка, на остальные отвечает 422.

**Три модели на одну сущность** — приём, который повторяется по всему проекту:

| Модель | Назначение | Особенность |
|---|---|---|
| `ItemCreate` | Что присылает клиент при создании | Все основные поля обязательны, `id` нет |
| `ItemUpdate` | Что присылает клиент при изменении | Все поля необязательны |
| `ItemOut` | Что сервер отдаёт | Наследует `ItemCreate` и добавляет `id` |

`id` нет во входной модели, потому что его назначает сервер. Клиент не должен выбирать идентификатор сам.

### 3.3. async и await

Uvicorn обрабатывает запросы в одном потоке с помощью цикла событий. Пока одна функция ждёт ответа от сети (`await`), цикл выполняет другие запросы.

- `async def` — функция, которая может приостанавливаться.
- `await` — точка, где функция отдаёт управление, пока ждёт.

В проекте настоящее ожидание есть в двух местах:

1. `await file.read(...)` — чтение загруженного файла;
2. `await client.post(...)` — запрос к Gemini, до 90 секунд.

Благодаря `await` сервер не зависает на полторы минуты, пока Gemini рисует картинку: остальные пользователи продолжают листать каталог.

Все остальные эндпоинты тоже объявлены как `async def`, хотя внутри ничего не ждут. Это безопасно: они работают только со словарями в памяти и выполняются мгновенно.

**Полезное следствие.** Между двумя `await` код выполняется без переключений. Поэтому в `create_order` проверка остатков и списание идут подряд, и два запроса не могут вклиниться друг в друга. Блокировки не нужны.

### 3.4. ООП в проекте

Классов в проекте немного, и это осознанно: сервисы написаны обычными функциями. Классы есть там, где они дают пользу.

**Наследование.**

- Ошибки: `AppError` — родитель, `NotFoundError`, `ConflictError` и остальные — потомки.
- Модели: `ItemOut(ItemCreate)` получает все поля родителя и добавляет `id`. `UserOut(UserCreate)` добавляет `id` и `photo_url`. `LookDetail(LookOut)` добавляет список товаров.
- Все модели наследуют `BaseModel`, все перечисления — `StrEnum`.

**Полиморфизм.** Обработчик `handle_app_error` один на все ошибки:

```python
return error_response(exc.status_code, exc.error, exc.detail)
```

Он не знает, какая именно ошибка пришла. Каждый потомок переопределяет атрибуты класса `status_code` и `error`, и одна и та же строка даёт 404, 409 или 502. Новая ошибка добавляется тремя строками, обработчик не меняется.

**Атрибуты класса и атрибуты объекта.** `status_code` и `error` заданы в теле класса и одинаковы для всех объектов этого класса. `detail` задаётся в `__init__` и у каждой ошибки свой.

**Инкапсуляция.** В `storage.py` словарь `_last_ids` начинается с подчёркивания: это договорённость «снаружи не трогать». Работать с ним нужно через функцию `next_id`.

**Абстракция.** Роутер не знает, как сервис хранит данные. Сервис не знает, что его вызвали по HTTP. `try_on.py` не знает, как устроен запрос к Gemini: он вызывает `llm.generate_try_on` и получает байты картинки.

**Почему сервисы не классы.** Своего состояния у них нет, все данные лежат в `storage`. Класс без состояния был бы просто обёрткой над набором функций. Модуль Python сам играет роль такого объекта: он создаётся один раз и общий для всех.

## 4. Разбор файлов

### 4.1. app/main.py — сборка приложения

Файл выполняется один раз, когда uvicorn импортирует `app.main:app`.

| Строки | Что происходит |
|---|---|
| [10](app/main.py#L10) | `llm.load_env()` читает файл `.env` и кладёт переменные в окружение |
| [11](app/main.py#L11) | `seed.load_seed()` заполняет каталог: 4 образа и 15 товаров |
| [13–15](app/main.py#L13-L15) | Папки `static/uploads` и `static/results` удаляются и создаются заново |
| [17](app/main.py#L17) | Создаётся приложение. `title` и `description` видны в Swagger |
| [18](app/main.py#L18) | Подключаются обработчики ошибок |
| [20–24](app/main.py#L20-L24) | Подключаются пять роутеров |
| [26](app/main.py#L26) | Папка `static` раздаётся как сайт |

**Зачем чистить папки при старте.** Данные в памяти сбросились, id пользователей начнутся заново с 1. Старый файл `user_1.jpg` принадлежал бы уже другому человеку. `ignore_errors=True` нужен, чтобы первый запуск не падал, когда папок ещё нет.

**Почему статика подключается последней.** Маршруты проверяются в порядке добавления. `mount("/")` перехватывает любой адрес, поэтому, стоя первым, он заслонил бы API. `html=True` означает, что по адресу `/` отдаётся `index.html`.

### 4.2. app/storage.py — данные

Семь словарей — это вся «база данных»:

| Словарь | Ключ | Значение |
|---|---|---|
| `items` | id товара | словарь товара |
| `looks` | id образа | `{"id", "title"}` |
| `users` | id пользователя | словарь анкеты |
| `fitting_rooms` | id пользователя | список позиций `{"item_id", "quantity"}` |
| `orders` | id заказа | словарь заказа |
| `try_ons` | id примерки | словарь примерки |
| `try_on_times` | id пользователя | список моментов запуска примерок, для суточного лимита |

Функции:

- **`next_id(kind)`** ([17](app/storage.py#L17)) — увеличивает счётчик нужного вида и возвращает новое число. Аналог автоинкремента в базе данных. Счётчик только растёт, поэтому id удалённого товара не выдаётся повторно.
- **`static_path(url)`** ([22](app/storage.py#L22)) — превращает адрес вида `/uploads/user_1.jpg` в путь на диске. `lstrip("/")` обязателен: если склеить путь со строкой, начинающейся на `/`, Python отбросит левую часть и получится путь от корня диска.
- **`delete_file(url)`** ([26](app/storage.py#L26)) — удаляет файл, если адрес задан. `missing_ok=True` не даёт упасть, когда файла уже нет.

### 4.3. app/seed.py — стартовые данные

- `LOOKS` — названия четырёх образов.
- `ITEMS` — 15 кортежей: название, категория, цвет, цена, остаток, номер образа, файл фото.
- `load_seed()` ([30](app/seed.py#L30)) проходит по спискам, получает id через `next_id` и кладёт словари в хранилище.

У последнего товара (серо-зелёная сумка) остаток 0. Это сделано специально: на нём видно состояние «нет в наличии», работу фильтра `in_stock` и то, что рекомендации такой товар не предлагают.

### 4.4. app/exceptions.py — ошибки

**Классы.** `AppError` — общий родитель с кодом 500. Потомки переопределяют код и короткое имя ошибки:

| Класс | Код | Имя | Где бросается |
|---|---|---|---|
| `BusinessRuleError` | 400 | `business_rule` | Примерочная пуста или переполнена, не хватает товара, нет фото, фото слишком большое |
| `NotFoundError` | 404 | `not_found` | Нет товара, образа, пользователя, заказа, примерки |
| `ConflictError` | 409 | `conflict` | Действие противоречит текущему состоянию |
| `UnsupportedMediaError` | 415 | `unsupported_media_type` | Файл не JPEG и не PNG |
| `TooManyRequestsError` | 429 | `too_many_requests` | Больше трёх примерок за сутки |
| `LLMError` | 502 | `bad_gateway` | Gemini не ответил, ответил ошибкой или не прислал картинку |

**400 и 409 — в чём разница.** 400 означает, что сам запрос нарушает правило («в примерочной не может быть больше 10 позиций»). 409 означает, что запрос нормальный, но мешает состояние других данных («товар лежит в чужой примерочной», «заказ уже отправлен»).

**Обработчики.**

- **`handle_app_error`** ([51](app/exceptions.py#L51)) — для всех своих ошибок. Берёт код, имя и текст из самого исключения.
- **`handle_validation_error`** ([55](app/exceptions.py#L55)) — для ошибок валидации Pydantic. У каждой ошибки есть путь к полю (`loc`) и сообщение (`msg`). Обработчик склеивает их в строку вида `body.price: Input should be greater than 0` и отдаёт с кодом 422.
- **`handle_http_error`** ([60](app/exceptions.py#L60)) — для стандартных ошибок фреймворка: несуществующий адрес (404), неподдерживаемый метод (405).
- **`handle_unexpected_error`** ([65](app/exceptions.py#L65)) — для всего остального. Отдаёт 500 с нейтральным текстом, чтобы не показывать клиенту внутренности сервера. Сама ошибка при этом попадает в консоль uvicorn.

**`register_exception_handlers`** ([69](app/exceptions.py#L69)) привязывает обработчики к типам ошибок. Обработчик для `AppError` срабатывает и на всех потомков.

**Почему `HTTPException` импортирован из `starlette`.** FastAPI построен поверх Starlette, и его `HTTPException` наследует класс из Starlette. Обработчик, привязанный к родителю, ловит оба варианта, включая 404 на несуществующий адрес, который создаёт сам Starlette.

**Что это даёт.** Любая ошибка приходит клиенту в одном формате: `{"error": "...", "detail": "..."}`. Фронту достаточно прочитать `detail` и показать пользователю.

### 4.5. app/schemas — модели данных

**[items.py](app/schemas/items.py)**

- `Category` — шесть категорий одежды.
- `ItemCreate` — название от 1 до 100 символов, категория, цвет до 30 символов, цена строго больше нуля, остаток от нуля, необязательные образ и фото.
- `ItemUpdate` — те же поля и ограничения, но все необязательны.
- `ItemOut` — `ItemCreate` плюс `id`.
- `LookOut` — образ со списком id товаров. `LookDetail` — он же плюс сами товары.

**[users.py](app/schemas/users.py)**

- `Gender`, `BodyType` — перечисления.
- `UserCreate` — имя, рост от 100 до 250, вес от 30 до 250, пол, тип фигуры, пожелания по стилю до 200 символов.
- `UserUpdate` — всё необязательно.
- `UserOut` — `UserCreate` плюс `id` и `photo_url`.

**[fitting_room.py](app/schemas/fitting_room.py)**

- `FittingRoomAdd` — id товара и количество (по умолчанию 1, минимум 1).
- `QuantityUpdate` — новое количество, минимум 1. Ноль запрещён: чтобы убрать товар, есть DELETE.
- `FittingRoomRow` — строка примерочной: товар целиком, количество, сумма по строке.
- `FittingRoomOut` — примерочная целиком: id пользователя, строки, общая сумма. Пример вложенных моделей: `FittingRoomOut` → список `FittingRoomRow` → `ItemOut`.

**[orders.py](app/schemas/orders.py)**

- `OrderStatus` — четыре статуса.
- `OrderItem` — позиция заказа: id товара, название, цена, количество.
- `OrderOut` — заказ. Поле `created_at` имеет тип `datetime`, в JSON оно превращается в строку формата ISO.
- `OrderStatusUpdate` — тело запроса на смену статуса.

**[try_on.py](app/schemas/try_on.py)**

- `TryOnStatus` — `done` или `failed`.
- `TryOnCreate` — список id товаров, от 1 до 3 штук. `min_length` и `max_length` здесь ограничивают длину списка.
- `TryOnOut` — примерка. `source: Literal["gemini", "mock"]` допускает ровно две строки, отдельное перечисление для этого не заводится.

### 4.6. app/routers — эндпоинты

Каждая функция роутера состоит из одной строки: вызвать сервис и вернуть результат. Ниже — что в них стоит заметить.

**[items.py](app/routers/items.py)** — каталог и образы, префикса нет.

| Функция | Маршрут | Заметки |
|---|---|---|
| `list_items` | GET `/items` | Пять необязательных фильтров из строки запроса. `category` принимает только значения `Category`, цены не могут быть отрицательными |
| `get_item` | GET `/items/{item_id}` | |
| `create_item` | POST `/items` | Тело — `ItemCreate`, код 201 |
| `update_item` | PATCH `/items/{item_id}` | Тело — `ItemUpdate` |
| `delete_item` | DELETE `/items/{item_id}` | Код 204, тела нет |
| `get_matches` | GET `/items/{item_id}/matches` | `limit` от 1 до 20, по умолчанию 4 |
| `list_looks` | GET `/looks` | Модель ответа `LookOut` |
| `get_look` | GET `/looks/{look_id}` | Модель ответа `LookDetail` |

Наглядный пример работы `response_model`: `list_looks` и `get_look` используют одну и ту же функцию сервиса, которая возвращает словарь с ключом `items`. В `LookOut` такого поля нет, поэтому в списке образов FastAPI его вырезает, а в `LookDetail` оставляет.

**[users.py](app/routers/users.py)** — префикс `/users`.

Путь `""` вместе с префиксом даёт ровно `/users`, без косой черты в конце.

`upload_photo` ([30](app/routers/users.py#L30)) — единственный роутер, где есть логика:

```python
data = await file.read(users_service.MAX_PHOTO_BYTES + 1)
```

Читается не весь файл, а максимум на один байт больше лимита. Если пришло ровно столько, файл слишком большой, и сервис ответит ошибкой. Так сервер не загружает в память файл на гигабайт только ради того, чтобы его отклонить.

**[fitting_room.py](app/routers/fitting_room.py)** — префикс `/users/{user_id}/fitting-room`.

Параметр `{user_id}` стоит в префиксе, поэтому он есть у каждой функции этого роутера. Четыре операции: посмотреть, добавить товар, изменить количество, убрать товар. Первые три возвращают примерочную целиком, чтобы фронт сразу показал новое состояние.

**[orders.py](app/routers/orders.py)** — префикса нет, потому что пути начинаются по-разному: `/users/{user_id}/orders` для создания и списка, `/orders/{order_id}` для чтения и смены статуса.

`create_order` не принимает тела: заказ собирается из того, что лежит в примерочной.

**[try_on.py](app/routers/try_on.py)** — единственный роутер с `await` при вызове сервиса, потому что `create_try_on` сам ждёт Gemini.

### 4.7. app/services/items.py — каталог и рекомендации

**Константы.**

- `NEUTRAL_COLORS` — белый, чёрный, серый, бежевый. Считается, что они сочетаются с любым цветом.
- `MATCHING_CATEGORIES` — какие категории дополняют какую. К верху подходят низ, обувь, сумка и верхняя одежда; к обуви — верх, низ и сумка; и так далее.

**`list_items`** ([19](app/services/items.py#L19)). Берёт все товары и по очереди применяет те фильтры, которые заданы. Цвет сравнивается без учёта регистра. Фильтр наличия записан как `(item["stock"] > 0) == in_stock`, поэтому `in_stock=false` возвращает именно закончившиеся товары, а не все подряд.

**`get_item`** ([34](app/services/items.py#L34)). Возвращает товар или бросает 404. Эту функцию вызывают все остальные сервисы, когда нужно проверить существование товара.

**`create_item`** ([40](app/services/items.py#L40)). Если указан образ, проверяет, что он существует. Превращает модель в словарь, добавляет id, сохраняет.

**`update_item`** ([49](app/services/items.py#L49)). Находит товар, берёт из запроса только заполненные поля, проверяет образ, обновляет словарь на месте.

**`delete_item`** ([58](app/services/items.py#L58)). Проходит по всем примерочным. Если товар у кого-то лежит, бросает 409. Это защищает от «висящих ссылок»: примерочная хранит только id товара, и при чтении сервер упал бы, не найдя его.

**`get_look`** ([67](app/services/items.py#L67)). Находит образ и собирает его товары. Связь хранится на стороне товара (поле `look_id`), поэтому список товаров образа каждый раз вычисляется перебором.

**`list_looks`** ([80](app/services/items.py#L80)). Вызывает `get_look` для каждого образа.

**`colors_match`** ([84](app/services/items.py#L84)). Два цвета сочетаются, если они одинаковые или хотя бы один нейтральный.

**`find_matches`** ([89](app/services/items.py#L89)) — рекомендации «дополни образ». Работает на правилах, без машинного обучения:

1. **Отбор кандидатов.** Товар должен быть другим, быть в наличии, относиться к подходящей категории и сочетаться по цвету.
2. **Сортировка.** Ключ сортировки `other["look_id"] != item["look_id"]` даёт `False` для вещей из того же образа и `True` для остальных. `False` меньше `True`, поэтому вещи из того же образа оказываются первыми. Сортировка в Python устойчивая: внутри групп порядок не меняется.
3. **Разнообразие.** Первый проход берёт по одной вещи на категорию. Второй добавляет оставшихся кандидатов в конец.
4. **Обрезка** до `limit`.

Пример для кремовой блузки (id 1, верх, бежевый, образ 1). Бежевый нейтральный, значит по цвету подходит всё. Подходящие категории: низ, обувь, сумка, верхняя одежда. После сортировки первыми идут вещи образа 1: брюки, жилет, туфли. Сумки в образе 1 нет, поэтому четвёртой берётся бордовая сумка из образа 2. Серо-зелёная сумка не попадает вообще: её нет в наличии.

### 4.8. app/services/users.py — анкета и фото

**Константы.** `ACTIVE_STATUSES` — заказ считается активным, пока он ожидает оплаты или оплачен. `MAX_PHOTO_BYTES` — 5 МБ.

**`create_user`** ([23](app/services/users.py#L23)). Сохраняет анкету, выставляет `photo_url = None` и сразу создаёт пустую примерочную. Благодаря этому остальной код может обращаться к `storage.fitting_rooms[user_id]` без проверки, существует ли ключ.

**`update_user`** ([32](app/services/users.py#L32)). Обновляет только присланные поля.

**`save_photo`** ([38](app/services/users.py#L38)).

1. Проверяет, что пользователь существует.
2. Определяет формат по первым байтам файла. У JPEG файл начинается с `FF D8 FF`, у PNG — с `89 50 4E 47`. Расширению и заголовку `Content-Type` доверять нельзя: их задаёт клиент и может подделать.
3. Проверяет размер.
4. Удаляет старое фото. Это нужно, потому что расширение могло смениться, и иначе остался бы лишний файл.
5. Сохраняет файл под именем `user_{id}.{расширение}`.

Имя файла сервер придумывает сам и не использует имя от клиента. Это закрывает атаку, при которой в имени файла передают `../../` и записывают файл в чужую папку.

**`delete_user`** ([55](app/services/users.py#L55)).

1. Сначала проверка: при активном заказе удаление запрещено (409).
2. Только потом удаление: фото, все примерки вместе с картинками, история лимита, анкета, примерочная.

Порядок важен: если бы проверка шла после начала удаления, пользователь мог бы остаться наполовину удалённым. При переборе примерок используется `list(...)`, потому что нельзя удалять элементы из словаря, по которому идёт цикл.

### 4.9. app/services/fitting_room.py — примерочная

Примерочная хранится как список позиций `{"item_id", "quantity"}`. Товар целиком в неё не копируется.

**`find_position`** ([12](app/services/fitting_room.py#L12)). Ищет позицию с нужным товаром, возвращает её или `None`.

**`get_room`** ([19](app/services/fitting_room.py#L19)). Для каждой позиции подтягивает актуальный товар из каталога, считает сумму по строке и общую сумму. Суммы нигде не хранятся и вычисляются при каждом чтении: если цена товара изменится, примерочная сразу покажет новую.

**`add_item`** ([31](app/services/fitting_room.py#L31)).

- Если товар уже лежит в примерочной, количество складывается, новая строка не создаётся.
- Лимит в 10 позиций проверяется только при добавлении нового товара. Увеличивать количество уже лежащего можно.
- Итоговое количество не может превышать остаток на складе.

**`update_quantity`** ([51](app/services/fitting_room.py#L51)). Ставит точное количество. Если товара в примерочной нет — 404, если на складе меньше — 400.

**`remove_item`** ([63](app/services/fitting_room.py#L63)). Убирает позицию или отвечает 404.

**Важно для защиты.** Товар в примерочной не резервируется: остаток на складе не уменьшается. Двое могут положить к себе последнюю вещь. Кто первым оформит заказ, тот её получит, второй получит 409.

### 4.10. app/services/orders.py — заказы

**`ALLOWED_TRANSITIONS`** ([10](app/services/orders.py#L10)) — таблица разрешённых переходов между статусами:

```
pending ──► paid ──► shipped
   │         │
   ▼         ▼
cancelled  cancelled
```

Из `shipped` и `cancelled` переходов нет: это конечные состояния. Такая схема называется конечным автоматом. Вместо набора `if` все правила записаны в одном словаре.

**`create_order`** ([18](app/services/orders.py#L18)).

1. Пользователь должен существовать, примерочная не должна быть пустой.
2. **Первый проход** — только проверка: хватает ли каждого товара.
3. **Второй проход** — списание остатков и сбор позиций заказа.
4. Создаётся заказ со статусом `pending` и временем в UTC.
5. Примерочная очищается.

Два прохода нужны, чтобы заказ создавался целиком или не создавался вообще. Если бы проверка и списание шли в одном цикле, то при нехватке третьего товара первые два оказались бы уже списаны.

Название и цена товара **копируются** в заказ. Если товар потом подорожает, будет переименован или удалён, заказ останется таким, каким был в момент покупки.

Нехватка товара здесь даёт 409, а не 400, как в примерочной. Причина: когда пользователь клал товар, его хватало, но с тех пор его купил кто-то другой. Запрос правильный, изменилось состояние.

**`list_user_orders`** ([57](app/services/orders.py#L57)) и **`get_order`** ([62](app/services/orders.py#L62)) — чтение.

**`change_status`** ([68](app/services/orders.py#L68)). Сверяет переход с таблицей, на запрещённый отвечает 409. При отмене возвращает товары на склад. Проверка `if row["item_id"] in storage.items` нужна на случай, если товар успели удалить из каталога.

## 5. LLM: AI-примерка

Две части: [app/services/try_on.py](app/services/try_on.py) решает, можно ли делать примерку и что отправить, [app/llm.py](app/llm.py) выполняет сам запрос.

### 5.1. Что такое обращение к LLM в этом проекте

Gemini — модель Google, которая принимает текст и картинки и может вернуть картинку. Своей модели на сервере нет: бэкенд отправляет обычный HTTP-запрос в облако Google и получает ответ. Для бэкенда это такой же внешний сервис, как платёжный шлюз.

Отправляется одно сообщение из нескольких частей:

1. текст с инструкцией;
2. фото пользователя;
3. фото каждой выбранной вещи.

В ответ приходит JSON, внутри которого лежит готовое изображение.

### 5.2. services/try_on.py: `create_try_on` по шагам

([19](app/services/try_on.py#L19))

**Шаг 1. Проверки, которые ничего не стоят.**

- Пользователь существует (404).
- У него загружено фото (400).
- Все товары существуют (404).
- Категории не повторяются (400): нельзя примерить две пары обуви сразу. Заодно это отсекает один и тот же товар, указанный дважды.
- У каждого товара есть файл с фото (400).

Все дешёвые проверки идут **до** лимита и **до** обращения к Gemini. Ошибочный запрос не тратит ни попытку пользователя, ни деньги.

**Шаг 2. Суточный лимит** ([31–35](app/services/try_on.py#L31-L35)).

Для каждого пользователя хранится список моментов запуска. Из него отбрасывается всё, что старше 24 часов. Если осталось три записи или больше — 429. Иначе в список добавляется текущий момент.

Это «скользящее окно»: лимит считается не по календарным суткам, а за последние 24 часа от текущего момента.

История лимита лежит в отдельном словаре `try_on_times`, а не вычисляется по списку примерок. Поэтому удаление примерки из истории попытку не возвращает.

**Шаг 3. Запись создаётся заранее** ([38–48](app/services/try_on.py#L38-L48)).

Примерка сохраняется в хранилище ещё до вызова Gemini, со статусом `failed`. Статус меняется на `done` только в самом конце. Если что-то пойдёт не так, в истории останется честная запись о неудаче с текстом ошибки.

**Шаг 4. Генерация.**

- **Режим mock** (`LLM_MOCK=true`): Gemini не вызывается, в результат копируется исходное фото пользователя. Нужен, чтобы разрабатывать и показывать проект без ключа и без расходов.
- **Обычный режим**: вызывается `llm.generate_try_on`. При ошибке её текст записывается в примерку, после чего ошибка пробрасывается дальше (`raise` без аргументов), и клиент получает 502. Результат сохраняется в `static/results/{id}.png`.

**Шаг 5.** Статус меняется на `done`, записывается адрес картинки.

### 5.3. Вспомогательные функции try_on.py

**`item_photo`** ([67](app/services/try_on.py#L67)) — находит файл с фото товара и защищает от подмены пути.

Товар можно создать через API с любым `image_url`. Злоумышленник мог бы указать `/../../.env`, и сервер отправил бы в Gemini файл с секретным ключом. Защита: путь приводится к настоящему абсолютному виду через `resolve()`, после чего проверяется, что файл существует и лежит внутри папки `static`.

**`encode_image`** ([74](app/services/try_on.py#L74)) — готовит картинку к отправке. Тип определяется по расширению, содержимое кодируется в base64. Это способ записать произвольные байты обычными буквами и цифрами: в JSON нельзя положить бинарные данные напрямую.

**`build_prompt`** ([81](app/services/try_on.py#L81)) — собирает текст инструкции:

```
Одень человека с первого фото в вещи с остальных фото. Сохрани лицо, позу и фон.
Параметры человека: рост 170 см, вес 60 кг, тип фигуры average.
Вещи в порядке следования фото: Кремовая шёлковая блузка (бежевый), ...
Верни одно фотореалистичное изображение.
```

В промпте четыре части: задача, ограничения (что сохранить), данные из анкеты, требование к результату. Вещи перечислены в том же порядке, в котором идут их фото, чтобы модель могла сопоставить название с картинкой.

**`list_user_try_ons`**, **`get_try_on`**, **`delete_try_on`** — чтение и удаление. При удалении стирается и файл с результатом.

### 5.4. llm.py

**`load_env`** ([15](app/llm.py#L15)) — маленький самописный читатель файла `.env`. Пропускает пустые строки и комментарии, остальные делит по первому знаку `=`.

Используется `os.environ.setdefault`: переменная устанавливается, только если её ещё нет. Значит, настоящие переменные окружения имеют приоритет над файлом. Это важно для Docker, где переменные передаются через `--env-file`, а самого файла в контейнере нет.

**`generate_try_on`** ([26](app/llm.py#L26)).

1. Читает ключ. Если его нет, сразу бросает `LLMError`, запрос не отправляется.
2. Читает название модели, по умолчанию `gemini-2.5-flash-image`.
3. Собирает части сообщения: текст и картинки.
4. Выбирает один из двух вариантов подключения:

| | Google AI Studio (по умолчанию) | Vertex AI (`GEMINI_BACKEND=vertex`) |
|---|---|---|
| Адрес | `generativelanguage.googleapis.com` | `aiplatform.googleapis.com` |
| Ключ передаётся | В заголовке `x-goog-api-key` | В параметре адреса `?key=` |
| Тело запроса | Только содержимое | Плюс роль `user`, требование вернуть картинку и соотношение сторон 3:4 |

5. Отправляет POST с таймаутом 90 секунд. Генерация картинки занимает десятки секунд, обычного таймаута не хватило бы.
6. `raise_for_status()` превращает ответ с кодом 4xx или 5xx в исключение.
7. Достаёт из ответа список частей: `candidates[0].content.parts`.
8. Ищет часть с картинкой, декодирует из base64 и возвращает байты. Если картинки нет, бросает `LLMError`.

**Обработка ошибок** ([53–57](app/llm.py#L53-L57)).

- Gemini ответил ошибкой: полный текст ответа пишется в лог сервера, клиенту уходит только код. Клиенту незачем видеть внутренние сообщения Google.
- Всё остальное (таймаут, нет сети, неожиданная форма ответа): клиенту уходит название типа ошибки.

В обоих случаях получается `LLMError`, то есть 502 Bad Gateway. Этот код означает: наш сервер работает, но сервис, к которому он обращался, ответил плохо.

Логгер называется `uvicorn.error`: это стандартный логгер uvicorn, сообщения появляются в той же консоли, что и остальные сообщения сервера.

### 5.5. Меры безопасности вокруг LLM

| Мера | Где | От чего защищает |
|---|---|---|
| Ключ только в `.env` | `llm.py`, `.gitignore` | Утечка ключа через репозиторий |
| Лимит 3 в сутки | `try_on.py` | Неконтролируемые расходы |
| Максимум 3 вещи | `TryOnCreate` | Слишком большой и дорогой запрос |
| Фото до 5 МБ, только JPEG и PNG | `users.py` | Тяжёлые и посторонние файлы |
| Проверка пути к фото товара | `item_photo` | Отправка чужих файлов сервера в Gemini |
| Дешёвые проверки до вызова | `create_try_on` | Трата попыток на заведомо ошибочные запросы |
| Таймаут 90 секунд | `llm.py` | Вечное ожидание зависшего запроса |
| Режим mock | `try_on.py` | Зависимость разработки от ключа и сети |

## 6. Фронт коротко

Четыре страницы на чистом HTML, один файл стилей и один файл [static/app.js](static/app.js). Фреймворков нет.

- **Определение страницы.** У `<body>` есть атрибут `data-page`. Функция `start` ([473](static/app.js#L473)) читает его и запускает нужную инициализацию.
- **`api`** ([17](static/app.js#L17)) — обёртка над `fetch`. Отправляет JSON или форму с файлом, на ответ 204 возвращает `null`, при ошибке берёт текст из поля `detail`. Здесь и окупается единый формат ошибок бэкенда: один обработчик на всё.
- **Кто пользователь.** Входа нет. После создания анкеты её id сохраняется в `localStorage` браузера и подставляется в адреса запросов.
- **`escapeHtml`** ([48](static/app.js#L48)) — экранирует спецсимволы перед вставкой текста в страницу. Без этого товар с названием `<script>...` выполнил бы код в браузере посетителя (атака XSS).
- **Примерочная** ([378](static/app.js#L378)) — три независимых блока: позиции, заказы, история примерок. Кнопки статуса заказа рисуются по тем же правилам переходов, что и на бэкенде, но окончательная проверка всё равно на сервере.
- **Примерка.** На время запроса кнопка блокируется и показывается индикатор, чтобы пользователь не запустил вторую генерацию и не потратил лимит.

## 7. Слабые места

Критичных ошибок нет. Ниже то, что стоит знать и уметь объяснить.

### Ограничения учебного формата

1. **Нет авторизации.** Зная или подобрав `user_id`, можно открыть чужую примерочную, оформить заказ, удалить анкету. Фото пользователей доступны по прямой ссылке `/uploads/user_1.jpg`. Создавать и удалять товары может кто угодно. В реальном проекте нужны вход, токены и роли.
2. **Данные в памяти.** Перезапуск стирает всё. Нельзя запустить несколько копий сервера: у каждой были бы свои данные.
3. **Нет автотестов.** Проверка только вручную и скриптом на curl.

### Недочёты в логике

4. **PATCH не умеет обнулять поля.** В `update_item` и `update_user` используется `exclude_none=True`. Запрос `{"look_id": null}` не уберёт товар из образа: `null` просто игнорируется. Правильнее `exclude_unset=True`, который отличает «поле не прислали» от «прислали null».
5. **Неудачная примерка тратит попытку.** Время записывается в лимит до вызова Gemini. Если Gemini упал, одна из трёх попыток сгорела. С одной стороны, это защищает от бесконечных повторов; с другой — пользователь не виноват.
6. **Фото больше 5 МБ даёт код 400.** Точнее был бы 413 Payload Too Large.
7. **Товар в примерочной не резервируется.** Это осознанное решение, но о нём спросят (см. раздел 4.9).
8. **Заказы удалённого пользователя остаются.** Завершённые и отменённые заказы не удаляются вместе с анкетой. Их можно открыть по `/orders/{id}`, но список `/users/{id}/orders` уже отвечает 404.

### Недочёты в технике

9. **Запись файлов блокирует сервер.** `write_bytes` и `read_bytes` выполняются синхронно внутри `async`-функций. На файлах до 5 МБ это доли секунды, но при нагрузке стоило бы вынести в отдельный поток.
10. **Невнятная ошибка при отказе Gemini.** Если модель отклонила запрос (например, фильтром безопасности) и не прислала `candidates`, клиент увидит `Gemini request failed: KeyError`. Понятнее было бы отдельное сообщение.
11. **Нет повторных попыток.** При временном сбое Gemini запрос не повторяется.
12. **Ключ Vertex передаётся в адресе.** Адреса чаще попадают в логи, чем заголовки. Так устроен этот способ подключения, но это стоит знать.
13. **`AppError` не вызывает `super().__init__`.** Из-за этого `str(ошибка)` даёт пустую строку. На ответы клиенту не влияет, но в логах такая ошибка выглядела бы пустой.
14. **Код выполняется при импорте.** Чтение `.env`, загрузка данных и чистка папок стоят прямо в теле `main.py`. В FastAPI для этого предусмотрен механизм `lifespan`.

Пункты 4, 5 и 6 исправляются несколькими строками.

## 8. Вопросы, которые могут задать

**Почему FastAPI, а не Flask или Django?**
Проверка данных и документация получаются автоматически из типов. Есть встроенная поддержка `async`, которая нужна для долгого запроса к Gemini. Django слишком велик для проекта без базы данных.

**Чем PATCH отличается от PUT?**
PUT заменяет объект целиком, нужно прислать все поля. PATCH меняет только присланные. В проекте везде PATCH, поэтому в моделях `...Update` все поля необязательны.

**Почему 201, а не 200?**
201 Created означает, что в результате запроса появился новый объект. 200 — просто «успешно».

**Почему 204 при удалении?**
Возвращать нечего. 204 No Content говорит «успешно, тела ответа нет».

**Чем 422 отличается от 400?**
422 отдаёт Pydantic, когда данные неверны по форме: не тот тип, нарушено ограничение поля. 400 отдаёт сервис, когда форма верна, но нарушено бизнес-правило.

**Что будет, если два человека одновременно купят последнюю вещь?**
Первый запрос спишет остаток, второй получит 409. Гонки нет: в `create_order` нет ни одного `await`, поэтому проверка и списание выполняются без переключения на другой запрос.

**Зачем `response_model`, если сервис и так возвращает словарь?**
Он гарантирует форму ответа, вырезает лишние поля и попадает в документацию. Пример — список образов, где поле `items` отбрасывается.

**Где здесь ООП?**
Иерархия исключений с полиморфным обработчиком, наследование моделей (`ItemOut` от `ItemCreate`), перечисления, инкапсуляция счётчика id. Сервисы — функции, потому что состояния у них нет.

**Как заменить словари на базу данных?**
Поменять `storage.py` и тела функций в `services`. Роутеры, схемы и обработчики ошибок не меняются. Ради этого и сделано разделение на слои.

**Почему рекомендации без ИИ?**
Для сочетания категорий и цветов хватает правил. Это мгновенно, бесплатно и предсказуемо. ИИ используется там, где правилами не обойтись: в генерации изображения.

**Что происходит, если Gemini недоступен?**
`llm.py` бросает `LLMError`. В примерку записывается текст ошибки, статус остаётся `failed`. Клиент получает 502 с понятным сообщением. Остальной сайт продолжает работать.

**Почему 502, а не 500?**
500 означает ошибку в нашем коде. 502 означает, что наш сервер исправен, но внешний сервис, к которому он обратился, ответил плохо.

**Зачем mock-режим?**
Чтобы разрабатывать, тестировать и показывать проект без ключа, без интернета и без расходов.

**Где хранится ключ?**
В файле `.env`, который не попадает в git. В репозитории лежит только `.env.example` с пустым значением.

**Как сервер узнаёт, что файл действительно картинка?**
По первым байтам содержимого. Расширение и заголовок запроса клиент может подделать, а сигнатура файла у каждого формата своя.

**Почему в заказе хранятся название и цена, а не только id товара?**
Заказ — это снимок на момент покупки. Товар потом может подорожать или быть удалён, а заказ должен остаться прежним.
